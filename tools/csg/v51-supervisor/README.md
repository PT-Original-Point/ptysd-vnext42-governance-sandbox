# VNEXT5.1-R2 Supervisor source candidate

This source candidate implements deterministic read/reconcile/scheduling primitives for C7 and the anti-loop rules in C8. It is based on CP200 and is not installed on the Host.

Each wake accepts only the Project Directory locator as input authority. It rereads the Directory, current pointer, checkpoint, Mission, Policy, run/task/attempt/owner/effects, then requests a fresh runtime observation and recomputes READY lanes. Stale phase, task, attempt, or next-action text in a wake is recorded as ignored data. The core writes only a local evidence projection and never writes canonical state, starts Host work, or changes Mission lifecycle.

`runSupervisor` serializes wake cycles, emits only newly persisted evidence, and suppresses repeated identical operational error reports. A local source/test dispatch requires an exact SHA-256 logical-work key, durable pre-dispatch evidence, and a matching readback from the local-work adapter. Unknown outcomes, mismatched identities, and already-existing work park that unit until a fresh read resolves it. The adapter must enforce the declared local effects; Host mutation, Production, and worker provider-write effects are rejected by the scheduler.

Logical work fingerprints bind the current Spec and Mission, one logical unit, its acceptance contract, the canonical prestate, and true upstream inputs. Candidate output SHAs, reviewer state, Session IDs, and candidate-only checkpoint rollover are excluded so executor-created artifacts cannot reset the churn fuse.

The tests are source-local deterministic regressions. They do not establish Task Scheduler installation, reboot/crash survival, live provider access, live Factory MCP acceptance, or end-to-end 24x7 construction. Those require later C7 Host acceptance.

The Windows task profile and registration/rollback scripts describe one boot-triggered, single-instance Local Service task with automatic task-failure restart settings. Registration requires an exact package manifest and same-task readback; a same-name task with any different action, principal, trigger, or restart setting is rejected. The profile points to the future packaged `runtime/node.exe` and `bin/host-supervisor.mjs` entrypoint. Do not run the registration script until that exact entrypoint, package manifest, ACLs, and C7 live-install gate are present and accepted. The source tests validate the task contract only; they do not register the task or prove reboot/crash recovery.

The scheduler accepts a provider-derived concurrency cap from 1 through 4, enforces one valid owner per explicit mutable slice, and permits independent READY slices to start while another slice runs. An active owner with no exact mutable-scope identity is treated as project-wide and serializes new work. Only one active project integration lane is allowed. Duplicate scopes or active work above the cap are invariant violations.

Each READY or bounded-retry lane is checked against its dispatch gates before selection. A denied Host-mutation, Production, unknown-effect, identity, or capability lane is recorded as parked with its exact reason; it cannot shadow a lower-priority legal READY lane. The Supervisor never dispatches a denied lane.

## VNEXT5.2 D02 source-only shadow

The package entrypoint is bin/host-supervisor.mjs. Its supported modes are a single read-only shadow wake and read-only journal inspection. A shadow wake restores and validates the local append-only journal first, then rereads the fixed Project Directory, canonical pointer, checkpoint, Mission, Policy, and run/task/attempt/owner/effect bindings through the anonymous GitHub GET reader.

The D02 runtime never probes Host state and never dispatches work. After the canonical reread it loads the full 59-operation union (44-unit parent plus 15 P52 units with required parent adjustments) and reads a caller-supplied receipt/facts snapshot. Facts bind to the catalog digest, capture time, source-inventory receipt, and the exact current control head/checkpoint. Missing, stale, mismatched, or unknown input returns `READINESS_INCOMPLETE`. A 44-unit or single-slice subset never declares global exhaustion; only the full union with fresh complete facts may report `GLOBAL_EXHAUSTED`. Start dependencies determine whether work may start; completion dependencies determine whether a result can be accepted. A parked F01 lane therefore does not hide READY source or preflight work in other lanes. Invalid or absent FactoryMCP parks only the MCP route; unproven F01 task/cancel/receipt parks only dispatch. Native source work requires neither MCP, SYSTEM, future install phases, nor a fresh canonical owner.

The planned queue is always `SHADOW_PLAN_ONLY`: it may report READY and the selected next unit, while actual execution stays PARKED and Host dispatch, Host mutation, canonical write, and local-work dispatch all remain false. The live-observation port reports `UNAVAILABLE` with `attempted:true`, `provider_read:false`, `host_probe:false`, and an explicit reason; invoking that stub is not counted as a live observation. Trusted clock, owner lease expiry, and process liveness are separate inputs. Without a trusted clock the owner status remains unknown, and an expired lease does not revoke the owner.

New local receipts use journal schema V2 and include the full evaluated ID set, planned decision, scoped blockers, and input digests. Existing V1 records are validated under their original schema and retained in the same hash chain. A truncated or corrupt journal stops the affected runtime without repair or retry; source repair can continue independently.

Run the scoped source regressions with npm test from this directory. To run one shadow wake, pass --shadow-once, an explicit absolute --state-dir, and an absolute `--operation-facts` path (or place `operation-facts.json` inside the state directory). To inspect an existing journal without contacting GitHub, pass --inspect-journal and an existing absolute --state-dir. The Windows task profile and registration scripts remain uninstalled and are not invoked by either mode.

These local tests and a source-only shadow do not prove Host installation, Windows/VM reboot survival, live dispatch, canonical publication, semantic review, Production, or system acceptance. F01, D03, and all Human gates remain separate. Three-column reporting stays separated: Human-requested construction VNEXT5.2 (59-union), canonical CP200 / V5.1-R2 control state, and installed runtime UNKNOWN. Source, local, or structural PASS is never relabelled as semantic, live, or system PASS. Goal disappearance, context compaction, worker exit, or source PASS never completes the Mission; durable receipts restore stable work identity, UNKNOWN effects read back first, and lease expiry never implies process death.

## VNEXT5.2 F01 task adapter candidate

`lib/f01-executor-adapter.mjs` defines a provider-neutral task start/cancel/receipt boundary. It consumes the existing fleet selection, a fresh advertised capability observation, an exact operation permit, and an externally verifiable Hyper-V sandbox proof. It rereads the exact provider task receipt before start, rereads after start/cancel, and never retries an unknown effect. Cancellation does not release scheduler capacity until the provider receipt confirms both `CANCELLED` and `capacity_released:true`.

This is a noncanonical source candidate. No ACP/native CLI was invoked, no task or VM was created, and no provider port is connected in this session. The outer-review helper checks receipt structure only and explicitly requires a trusted reviewer readback. Therefore F01 route, isolation, task/cancel, receipt, and reviewer qualification remain pending until an actual route is negotiated and exercised under the operation's exact authority.
