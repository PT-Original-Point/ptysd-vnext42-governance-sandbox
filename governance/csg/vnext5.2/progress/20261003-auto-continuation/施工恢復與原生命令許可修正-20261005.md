# 施工恢復與原生命令許可修正

## 已確認的原因

1. 現有 Antigravity CLI 的 `permissions.allow` 有 15 條既有命令。當前兩個待執行測試的精確命令不在其中。舊成功任務曾先加入精確原生規則，之後恢復原設定；新派工沒有把所需命令與現有規則對齊。
2. 新的 literal echo 診斷亦被原生 `run_command` 拒絕：step54 的錯誤明示 `permission check failed` 與 `user denied permission`。這是工具紀錄，不能推論 Human 當晚親手按了拒絕，也不能斷言所有命令、全部模型都不可用。
3. 回收代理把缺專用 API 誤當 CLI 不可用，已由實際 `--help` 和同 conversation 派送推翻。CLI 傳送成功與代理內部命令取得許可是兩回事。
4. A00 仍寫廣告成果未收到，與既存 source receipt 矛盾。理由已改為「來源成果已收到；live admitted scope 與既有憑證讀路線尚未證明」，沒有宣稱 Ads 已驗收。
5. 舊交接程式會額外建立 Luna intent，且把 PREPARED 算在途；已移除。只有實際執行證據才算工作中。

## 恢復規則

- Root 只稽核、計劃、派工、回收、仲裁；產品 source 仍交鎖定的施工模型。
- 派工 intent 應列出所需的精確 command plan，先讀原生許可的摘要。字面未命中只是一項診斷，不能自製另一個比原生 matcher 更強的拒絕規則。
- 已實際遭拒、且許可 profile 沒變的同一命令，直接 park 該命令；不喚醒模型再試，不改寫命令、不換工具／代理取得同一受拒資源。
- 缺測試命令許可不取消 file-only source lane。沒有新缺陷時也不重做穩定 source，不能用空轉派工填滿工人。
- 同一 Project 的 Session／attempt／generation rollover 不重建運輸拒絕；已核准的命令與工作範圍可持續使用，新的命令差異單独處理。
- 優先使用原生 `permissions.allow` 與既有 CLI／SDK；不使用 skip-permissions、不增加第五個 MCP tool、不建立另一套 agent bus。
- 收件先驗 actual model/session、新訊息、write-set、digest、test scope；寫 ACK 後仲裁；一次移交全部精確 findings。實際完成或失敗才觸發下一件，沒有變更不輪詢模型。
- 完整 59-unit 計算與 recoverable lanes 保留。未完成的 phase 不是自動成立的 Human gate；local／static／structural 不冒充 live／installed／Production。

## 精確的原生許可修正包

`routes/resume-batch-20261004/native-permission-two-rule-proposal.json` 僅提議增加兩條當前測試命令。尚未修改原生設定或重試任何拒絕動作。因原生工具已明示拒絕，重新進入需 Human 明確核准這兩個精確動作，或在原生端解除相應拒絕並提供新 readback。這不是再次要求授權整個 Mission。

原生 command rule 的 CWD enforcement 尚未證明，不能吹成已完成的隔離。呼叫端仍必須綁定 exact CWD、來源 bytes、timeout/output/concurrency；正常 Node runner 子程序不能被一律禁止。
